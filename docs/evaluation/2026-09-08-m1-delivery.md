# M1: accepted consequence recovery

**Date:** 2026-09-08. **Baseline:** `db424029ef83e678b9347b9867b13c641beb6f94`,
verified by fetching `origin/main` and inspecting merged PR #93. This evidence
supports a draft implementation for review, not deployment or ADR ratification.
All databases used here are disposable; existing QA and player history are untouched.

## Failure evidence

The first four tests in `tests/test_delivery_recovery.py` were run before the
implementation: **4 failed**. They reproduced application loss in each queue
and partial `/act` acceptance after inserting a maturation or initial causal hop.
The original September 7 diagnostics identified the application-loss seams;
these tests assert recoverable behavior rather than pinning the defects.

A separate probe against an untouched archive of the baseline killed each
worker with **SIGKILL (exit -9)** immediately before application. For each queue:
**1 item before → 0 items after death, 0 history rows, 0 recovered on restart**.
[Measured JSON](2026-09-08-m1-delivery/baseline-kill.json) and the
[portable probe](2026-09-08-m1-delivery/baseline_kill_probe.py) are retained.
The probe takes an explicit checkout path, creates its own temporary databases,
and imports that checkout in each fresh process. To compare the original result:

```bash

mkdir -p /tmp/enfolded-m1-baseline
git archive db424029ef83e678b9347b9867b13c641beb6f94 | tar -x -C /tmp/enfolded-m1-baseline
.venv/bin/python docs/evaluation/2026-09-08-m1-delivery/baseline_kill_probe.py /tmp/enfolded-m1-baseline
```

## Trace and implemented boundary

| Stage | Staged causal hops | Verb maturation |
|---|---|---|
| Acceptance | Origin event/delta, pressure and whole initial ring share one transaction. HTTP solves include their attempt and applicable twin/constellation work. | SCALE_ACT, accepted absolute patch and initial causal ring share one transaction. HTTP, CLI and cast use the same helper. |
| Selection | Read a bounded list of due pending IDs, ordered by due time then ID. | Same, separate queue and default batch limit. |
| Claim | Acquire SQLite writer lock and recheck pending/due/retry state. No committed claim can outlive the process. | Same. |
| Application | Hydrate a fresh tree, interpret v1 law/legacy strength, run standard material/history/pressure/rearm handlers. | Resolve stored node, land the accepted absolute patch and SCALE_ACT_MATURED delta/version. |
| Continuation | Insert all required successors with parent/origin links in the effect transaction. | None: the originating act already scheduled its separate ripple cascade. |
| Completion | Commit effect/history/continuations plus retained outcome on the original row. | Commit delta/history plus retained outcome on the original row. |
| Notification | Broadcast after commit. Failure cannot roll back or replay an effect. | Same; a missed message is recoverable through world/history reads. |
| Error | Roll back the whole item, retain pending input, record error and capped retry delay. Continue other eligible work. | Same. |

See [ADR-019](../decisions/ADR-019-m1-sqlite-delivery.md) for exact schema,
transaction, compatibility, version, retry, and downgrade choices. ADR-013
remains Proposed; situation transitions and M2 action policies are not implemented.

## Regression coverage

`tests/test_delivery_recovery.py` contains **40 passing tests** at the focused
verification checkpoint. They include:

- Actual process termination before application, after the effect/history
  write, immediately before completion commit, and immediately after commit,
  for **both queues**; termination after a causal continuation insert; termination
  during both initial scheduling paths. Recovery uses a fresh spawned interpreter.
- Stable-ID redelivery, including duplicate candidates presented by two concurrent
  processes. Effects, historical deltas/versions, pressure, and continuations
  match uninterrupted execution. Completed work is never made retryable.
- Exceptions after application and continuation insertion; failure before a
  database commit; an acknowledgment error after the database actually committed.
  A failed item never leaves a partial delta or an unrecorded successor gap.
- Persistently invalid work retains input and an error through 13 attempts while
  valid work progresses. Future versions remain pending rather than being
  interpreted by current code; malformed JSON and non-object payloads also remain pending. Missing nodes have explicit terminal outcomes.
- Initial scheduling rollback through the real request handlers, CLI, and cast;
  retrying a puzzle solve in the same process after failure; two concurrent HTTP
  kindles and an authoritative `/world` read after maturity.
- A real schema-17 database upgraded to 18 with both pre-law and `_hop` causal
  rows and an absolute maturation. Old row fields, born nodes, pinned hinge,
  and historical rows compare equal across migration. Legacy strengths land
  as **0.5** versus **0.25**. Pending v18 backup → drain → restore → new-process
  recovery reproduces the same history and state. A v17 rollback backup also
  preserves all three pending items when restored and upgraded again.

The HTTP overlap result intentionally remains two accepted patches and two
landing deltas, with the same final absolute density. Collapsing those acts or
turning them into additive contributions would silently implement M2.

The dedicated browser tests drive **Kindle** in both shipped clients, kill the
local server with pending work, start a new server against the same test database,
let the actual pump deliver it, and reload after deliberately missing the
notification. The explorer also now keeps a delayed patch out of its live property
panel until it lands; previously its direct response path projected it early.
Browser scope is desktop recovery, not M5's mobile/scene promotion gate. At the
default 720px viewport the explorer's fixed panels obstructed the action button;
these recovery tests use 1440×1100. That existing layout issue is separate.

## Limits

This is database application idempotency per queue ID, not request or notification
transport deduplication. An `/act` retried by a client remains a distinct legacy
action. Previously lost work has no reliable payload to recover. The migration
does not invent missing origins or rewrite historical facts. Unsupported or
persistently failing inputs need operator inspection. No new cleanup policy,
external queue, situation engine, rule-authoring system, or deployment is included.
